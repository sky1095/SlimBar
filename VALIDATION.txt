Notarization rejection and fix (2026-09-18):
The first submission came back Invalid. The log named one cause, three
times over: Contents/Resources/simslim was not Developer ID signed, carried no
secure timestamp, and had no hardened runtime. Replacing codesign --deep with
explicit inside-out signing had covered Sparkle's helpers but not the bundled
backend, which --deep had been signing implicitly.
build.sh now signs simslim with the same identity and flags as everything else.
An audit of every Mach-O in the bundle confirms all seven binaries carry the
project's team identifier, the hardened runtime, and a secure timestamp.
The signed simslim still runs under the hardened runtime and returned valid JSON
from "list --json"; the 48-assertion suite passes against it.
release.sh gained two guards: a preflight that audits every executable before
submitting, and an explicit status check, because notarytool exits 0 even when
the result is Invalid, which is why the failed run reached the stapler and
produced an unreadable "Error 65" instead of stopping at the real error.
The preflight was tested both ways: it names every offending file on an ad-hoc
build and passes a Developer ID build.
Notarization has still NOT succeeded; no release has been published.

Branch and tag rulesets (2026-09-18):
main is protected by an active ruleset: pull request required, force pushes and
branch deletion blocked, and review threads must be resolved. One approving review is required and it must
come from a code owner; .github/CODEOWNERS assigns every path to the repository
owner, so no change can merge without the owner's review. GitHub does not allow
approving your own pull request, so the owner's own pull requests are merged
through the bypass rather than by self-approval.
Required status checks were left out because the repository has no CI workflow;
requiring them would have blocked every pull request indefinitely.
Release tags matching v* are protected against deletion and force-update, so a
published tag cannot be moved out from under the Sparkle feed.
Both rulesets are bypassed by the Admin repository role, which only the owner
holds, so direct pushes to main and changes to release tags are possible for the
owner alone. The bypass is bound to the role rather than to an account, so
granting admin to anyone else would extend that power to them; repository
rulesets cannot name an individual user as a bypass actor.
